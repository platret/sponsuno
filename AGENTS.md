# AGENTS.md – Sponsuno website

Read this first in every session. It says what this project is, how it is built, and which rules are not negotiable. Visual rules live in [DESIGN.md](DESIGN.md); read that before touching anything visible.

## What this is

Sponsuno is a startup project of a four-person team in the programme Youngpreneurs Zürich 2026/27 (https://youngpreneurs.org/zuerich/). The planned platform matches athletes, sport clubs and culture clubs with sponsors from their region, starting in German-speaking Switzerland (long term: DACH). A personal AI sponsoring manager is planned to help with the partnership afterwards, plus separately billed marketing services (photo, video, content).

This repo holds:

1. The public **landing page** (`/`). It explains the idea and collects interest on a waitlist. Since November 2026 it is kept short; since the D1 redesign (2026-11-24): hero with the «Punkte» field, statement (ProofLine), «Heute» (problem), «Mit Sponsuno» (a horizontal row of four cards with drawings and arrow buttons), how it works (segmented switch), «Für wen» (two audience columns), team row (TeamStrip, `#team`), FAQ (HomeFaq, `#fragen`, all of `faq.items`, with the FAQPage JSON-LD in the landing page head), waitlist (centred). Everything else is parked: the site is the landing page plus Impressum, Datenschutz, the 404 page and `/warteliste/bestaetigt/`. The rest lives on topic pages.
2. Three **topic pages** reached from the header: `/kosten/` (with "Nicht nur Geld"), `/fragen/`, `/ueber-uns/` (team and project status).
3. The legal pages `/impressum/` and `/datenschutz/`.
4. A **404 page** (`dist/404.html`), which Cloudflare serves with status 404 for every unknown URL.
5. The **waitlist route** `POST /api/warteliste` (Cloudflare Worker, `worker/`) for the Brevo double opt-in, and its landing page `/warteliste/bestaetigt/` (noindex). Built but dormant until the team finishes the Brevo setup (see "Waitlist" and "Deploy").
6. **Parked sources** (not built, not linked, not reachable; see "Parked (not built)"): the topic pages `/kosten/`, `/fragen/`, `/ueber-uns/` (since 2026-11-25, owner: "just the main page for now"; their old URLs 301 to `/#fragen` and `/#team`), `/fuer-firmen/` and `/ki-manager/`, the four guide pages (Ratgeber) with their Word templates, and the clickable product preview (`/demo/`, `src/demo/`).

**The product does not exist yet.** No page may claim that it works today. Since 2026-11-10 the site still reads like a confident SaaS page before its launch (see "Rules for copy": product voice, one launch signal per page).

- Live: https://sponsuno.ch (www.sponsuno.ch redirects to sponsuno.ch)
- Repo: https://github.com/platret/sponsuno (public)
- Language of the page: German, Swiss spelling, formal "Sie"

## Commands

Node 22.18 or newer (`engines` in `package.json`; CI uses the latest 22): `npm test` relies on Node's built-in TypeScript type stripping, and `@axe-core/playwright` 4.14 needs 22.12.

```bash
npm install
npm run dev        # http://localhost:5173/
npm run build      # typecheck, client build, prerender into dist/
npm run preview    # serve dist/ at http://localhost:4173/
npm run typecheck
npm run fonts      # only after changing the font subsets: rewrites src/assets/fonts/ and src/styles/fonts.css (commit them)
npm run photos     # only after replacing a photo in src/assets/photos/: rewrites its AVIF versions (commit them)
npm test           # unit tests of the Worker (worker/*.test.ts, node --test, Brevo mocked)
```

`npm run build` must pass before every commit. CI also runs `npm run typecheck`, `npm test`, `npm run check:dist`, a `wrangler deploy --dry-run` and `npm run test:e2e` on every PR (see "CI"); still verify visual changes in a browser (see "Before you finish").

## Architecture

Vite 8 (Rolldown) + React 19 + TypeScript (strict). No UI framework, no CSS framework. One small Cloudflare Worker script (`worker/`) answers `/api/*` only; everything else is static assets. `vite` and `@vitejs/plugin-react` are pinned to exact versions, and `overrides` in `package.json` pins Rolldown (Vite allows newer patches): take only releases at least two weeks old, and move the pins together.

### Conventions that the code relies on

- **What the landing page bundle carries**: `main-*.js` imports `content.ts`, and the bundler keeps only what the landing page code reads. Never read `guides`, `legal` or other page-only objects from code the landing page reaches (`App.tsx` and its components, or a top-level constant in `content.ts` that one of them uses), and never index them with a variable key (`guides[id]` keeps every guide): either ships that whole text to every visitor. Use the small exports instead: `contact` (address and e-mail; `legal.contact` is the same object), `guideTitles` (the guides' H1s), `pageMeta()`. `npm run check:dist` fails when a script of the landing page (the module script, its modulepreloads and everything they import statically) contains a marker sentence of the legal pages or the 404 page (`FOREIGN_TEXT` in `scripts/check-dist.mjs`; the parked guides and `/fuer-firmen/` get theirs back when they are built again). Known leftovers: `pages.ts` (with `parkedPages`) and a few top-level constants of parked content that call `pageMeta()` (the bundler cannot prove them pure) are in `main-*.js`; small, within budget.
- **Copy** comes from `src/content.ts`. Exceptions: a few accessibility labels are inline (skip link in `App.tsx`, nav and logo labels in `Header.tsx`, `aria-label` in `Footer.tsx`, the footer wordmark). Check those too when reviewing copy.
- **SSR-safe components**: the page is prerendered at build time. Never touch `window`, `document`, `matchMedia` or `localStorage` at module top level or during render; only inside effects or event handlers.
- **Motion gate**: `html.motion` is set only when the visitor does not prefer reduced motion (`motionEnabled()`). `html.scroll-fx` is set on top of it only when the browser supports `animation-timeline: view()` (`scrollFxEnabled()`). Exception: the parked `/ki-manager/` sets `html.scroll-fx` alone (see "Topic pages"). Every animation needs a still fallback that shows the final state: the static styles of an element are its final state, keyframes describe only where it starts.
- **Scroll motion** (plan and primitives in DESIGN.md → Motion): add `data-scroll="rise | fade | zoom-in | photo | frame | draw-x | draw-y | recede | group"` and keep `data-reveal=""` next to it where Firefox should still get the fade. Tune with the `--scroll-*` custom properties, never by copying the primitives. Section-specific scroll animations go in the section stylesheet under `.scroll-fx` and use `animation-timeline: view()` or a named `view-timeline`; set `animation-timeline` and `animation-range` after any `animation` shorthand (the shorthand resets them). Only `opacity`, `translate`, `scale`, `clip-path`. One `data-scroll` per element; never on an element that has its own CSS animation (wrap it). Every element must be final once its top is about 60 % down the viewport, and nothing visible at scroll 0 may start hidden. Elements at the end of the page (footer) end their range at `entry min(100%, var(--scroll-dist))` (final once fully in view, or earlier). Named `view-timeline`s set `view-timeline-inset: 0px`; never put `scale`/`translate` animations on an SVG element (wrap it in a `span`). A shared focus guard in `site.css` shows any `data-scroll` block holding focus in its final state; do not add per-section copies. Pinned sections: budget in DESIGN.md (max two, each at most one extra viewport, never below 600 px); none is used while `/ki-manager/` is parked (its KI-Manager bento, `ai.css`, was the one; see "Topic pages").
- **Hero field** (since 2026-11-24, owner's direction): `Hero.tsx` starts `lib/heroField.ts` in an effect (never during render). Without JS or WebGL the hero is plain Tintenblau. The canvas is `aria-hidden`; the pause toggle (`.hero-pause`, `aria-pressed`, `hero.pauseLabel`) appears once the field runs. Sections that are Tintenblau carry `data-header-dark` (hero, «Mit Sponsuno», waitlist): the header stays Tintenblau over them and turns to the page surface over Hafer.
- **Scroll story** (removed 2026-11-24; history only, `Story.tsx` in git): right under the hero, in place of the old Problem section (its copy, `problem` in `content.ts`, is the story's H2 and first steps). Text steps are normal content; two IntersectionObservers trigger one position check that sets `data-step` on the sticky stage (never stale after a jump or reload); CSS transitions do the rest. To move an item, edit the table in `lib/storyLayout.ts` (positions in % of the stage, per state, desktop and phone), not the CSS. All stage labels live in `content.ts` → `story`. Without JS, on screens up to 560 px tall and on phones with reduced motion every step shows its own static snapshot; keep that path complete when adding steps. The snapshots are prerendered; after hydration `Story.tsx` drops them while the stage is pinned (its `PINNED` query mirrors the "Pinned" media query in `story.css`: change both together). The hero start frame (`Hero.tsx`: input tiles from `story.heroInputs`, SVG wires, node, the "Passende Partner" window with `story.pairs`) and the stage use different papers (`story.papers`); keep it that way. The hero wires are drawn 1:1 in px: when you change tile height, gap or count in `hero.css`, redraw the paths in `Hero.tsx` (`WIRES`).
- **Reveals**: `data-reveal=""` alone fades an element in once (`observeReveals()` in `App.tsx`, CSS in `site.css`). Under `.scroll-fx`, elements that also carry `data-scroll` are skipped by the observer and the fade is neutralised.
- **No animation or scroll libraries** (GSAP, Lenis, Three.js were removed in the November 2026 redesign), no smooth-scroll override, no JS that runs on every scroll frame (use IntersectionObserver or CSS scroll timelines). One exception (owner's direction 2026-11-25): **Motion** (`motion`, pinned) animates the drawings of «Mit Sponsuno», and only there: `FeaturesLive.tsx` is loaded by `Features.tsx` after hydration and only when `html.motion` is set (its own chunks, with `lib/motionFeatures.ts` via `LazyMotion`); the first JavaScript carries none of it. The drawings live Motion-free in `featuresArt.tsx` (plain SVG in their final state) and get Motion's `m` elements through the `ArtKit` context. `MotionConfig reducedMotion="user"`. Icons: **Lucide** (`lucide-react`, pinned), imported per icon.
- **Theme (one light theme, since 2026-11-17)**: the light/dark switch of 2026-11-10 is gone on the owner's direction (DESIGN.md → Theme). No switch, no theme script, no `html[data-theme]`, no `prefers-color-scheme` rules and no dark palette; do not bring any of it back without the owner. Colours: section CSS uses the role tokens of `tokens.css` (`--bg`, `--bg-alt`, `--surface`, `--heading`, `--text`, `--line`, `--accent-text`, `--btn-*`, `--focus`) for the page surface and its text; surfaces that are graphit by design (hero, story, KI device, waitlist, footer, the static header and page head band) use the raw design-system tokens (`--graphit`, `--graphit-2`, `--kalk`, `--steel`, `--brass` …). Never use `--paper`, `--kalk-2`, `--ink`, `--rule` or `--brass-dark` for a page surface or its text in new CSS. Every HTML entry carries `<meta name="color-scheme" content="light">` (`scripts/prerender.mjs` fails without it) and `<meta name="darkreader-lock">`; `tokens.css` sets `color-scheme: light` on `:root`, so form controls and scrollbars stay light under a dark system setting, and Safari's Adaptive Dark Mode and extensions such as Dark Reader leave the CD colours alone. `theme-color` is Tintenblau (`#1A2B40`) on every page, because every page opens on Tintenblau (D1). The published pages store nothing in the browser (no `localStorage`, no cookies; the theme key `sponsuno-theme` and its Datenschutz section are gone with the switch): anything that starts storing needs its own section in the Datenschutzerklärung. Give every surface its own background and text colour (never rely on browser defaults).
- **Section styles**: each section imports its own stylesheet from `src/styles/sections/` and prefixes its classes.
- **In-page links**: plain `<a href="#id">`. `App.tsx` intercepts them, scrolls below the fixed header and moves focus. A handler that does its own scrolling calls `preventDefault()`.
- **Links between pages**: build them with `pageHref()` / `siteHref()` from `lib/links.ts` (base path). Footer link hrefs in `content.ts` are `#id` (landing page section) or `path/` (page); on sub-pages section links lead back to the landing page. Only `#ablauf`, `#fuer-wen`, `#problem`, `#warteliste` and `#top` exist on the landing page now; link everything else to its page (`pageMeta(id).path`). Never link a parked page (check-dist fails: no file in `dist/`).
- **Navigation**: one list, `nav` in `content.ts` (since 2026-11-25 landing page anchors only, in page order: So funktioniert es → `#ablauf`, Über uns → `#team`, Fragen → `#fragen`; the topic pages are parked), rendered by `Header` and `MobileMenu` on the landing page (`siteHref(href, true)`: the anchor stays in-page, `App.tsx` scrolls it) and by `PageHeader` on every static page (`siteHref(href, false)`: `/#ablauf`), each followed by the waitlist button. `PageHeader` marks the current page with `aria-current="page"` via `navCurrent()`. Static pages have no JS, so below 961 px their nav sits in a native `<details>` menu; unlike the landing page menu it does not close on Escape or when focus leaves it (accepted: it scrolls away with the page and covers no focused element). Both headers use the same gaps (`.header-inner`, `.lg-header-inner`: 2rem, 1.25rem from 1140 px down), so the nav does not jump between pages. The static header is not fixed, so static pages set `scroll-padding-top: 1rem` (`legal.css`) instead of the landing page's header offset.
- **Static page head** (since 2026-11-10): every topic page, guide, legal page and the 404 page opens like the landing page, on Graphit: the graphit `PageHeader` (Kalk loop wordmark, Messing pill Warteliste button) and under it, as the first child of `<main>`, the graphit page head band (`PageBand`: the H1 and its intro; legal pages add the date, the parked guides the byline and `/fuer-firmen/` its launch note). The band's H1 keeps the id the article or section below points its `aria-labelledby` at.
